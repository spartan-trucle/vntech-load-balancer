# 12.3 Algorithms — research notes

Source material for the 12.3 slides (Khanh). Sources at the bottom.

---

## 0. Framing for the section

Every LB algorithm answers one question: **"given this request, which backend?"** They differ in how much they know:

| Knows nothing | Knows a counter | Knows live load | Knows the request key |
|---|---|---|---|
| Random | Round robin, Weighted RR | Least conn, P2C, least time | IP hash, consistent hash, sticky cookie |

Trade-off to repeat on every slide: **more information → better choice, but more state, more cost, and stale info can hurt.**

---

## 1. Random

- Pick a backend uniformly at random (or proportional to weight).
- **No state, no coordination** — every LB instance can do it independently.
- Downside: variance. Balls-into-bins math: throw *n* requests at *n* servers randomly → the busiest server gets **~ log n / log log n** requests while the average is 1. Short-window load is lumpy.
- Surprising upside (Envoy docs): random **behaves better than round robin when there is no active health checking** — RR sends the dead host's turn to the *next* host in the list, so the host right after a failed one gets double traffic. Random spreads it.
- HAProxy benchmark: pure random gave "disastrous" distribution under high contention.

## 2. Round Robin

- Keep a counter, pick `servers[i++ % n]`. Default in NGINX, HAProxy (`roundrobin`), ALB (`round_robin`), Envoy (`ROUND_ROBIN`).
- **Perfectly even request *counts*** — but counts ≠ work. A 3 s export and a 5 ms ping are both "one turn".
- Blind to backend health/speed: a slow or GC-pausing pod keeps getting 1/n of traffic and its queue grows (→ our 3.4 simulation).
- With many LB instances, each keeps its own counter → globally it looks close to random anyway.
- HAProxy: `roundrobin` is dynamic (weights can change at runtime, up to 4095 servers); `static-rr` has no limit but weights are fixed.

## 3. Weighted Round Robin

- Give bigger machines more turns: weight 5 : 1 : 1.
- **Naive WRR** produces bursts: `a a a a a b c` — server *a* gets 5 in a row, b/c sit idle.
- **Smooth WRR (NGINX, since 2012)** — interleaves picks:
  1. For every peer: `current += weight`
  2. Pick the peer with the highest `current`
  3. That peer: `current -= total_weight`

  Worked example, weights a=5, b=1, c=1 (total 7):

  | step | current before pick (a, b, c) | pick | after (a, b, c) |
  |---|---|---|---|
  | 1 | 5, 1, 1 | a | −2, 1, 1 |
  | 2 | 3, 2, 2 | a | −4, 2, 2 |
  | 3 | 1, 3, 3 | b | 1, −4, 3 |
  | 4 | 6, −3, 4 | a | −1, −3, 4 |
  | 5 | 4, −2, 5 | c | 4, −2, −2 |
  | 6 | 9, −1, −1 | a | 2, −1, −1 |
  | 7 | 7, 0, 0 | a | 0, 0, 0 ← back to start |

  Result: **`a a b a c a a`** instead of `a a a a a b c`. Same ratio, no bursts.
- NGINX also keeps an `effective_weight` that drops temporarily when a peer fails, then recovers.
- Where weights come from: instance size, canary (95/5), gradual rollout, slow start.
- Dynamic weights: Envoy *client-side WRR* computes weights from backend load reports (ORCA): `qps / (utilization + eps/qps × error_penalty)`.

## 4. Least connections (context for P2C)

- Pick the backend with the fewest in-flight requests. NGINX `least_conn`, HAProxy `leastconn`, ALB `least_outstanding_requests`.
- Self-correcting: a slow backend finishes fewer → keeps more in flight → gets picked less.
- Cost: O(n) scan (or a heap) per request, and it needs *accurate, fresh* counts.
- **Herd problem**: with several LBs (or stale counts), everyone sees the same "emptiest" server and all send to it at once → it becomes the busiest → everyone jumps to the next one. Oscillation.

## 5. Power of Two Choices (P2C)

**Algorithm:** pick 2 backends at random, send to the one with fewer in-flight requests.

**The math (Azar et al. 1994; Mitzenmacher 1996 PhD thesis):**
- 1 random choice → max load ≈ **log n / log log n**
- 2 random choices → max load ≈ **log log n / log 2** — an *exponential* improvement
- 3 choices only improves by a constant factor → "two is the sweet spot"
- Slide line: *"Going from 1 → 2 choices is a huge win. Going from 2 → 3 barely matters."*

**Why it beats "least connections" in real systems:**
- O(1) per request instead of O(n).
- Robust to **stale information**. Marc Brooker's simulation (10 servers, load info refreshed every 10–70 s): best-of-all was excellent with fresh data but *catastrophically* bad with stale data (herding); **best-of-two was the best performer across all refresh intervals**; random was bad throughout.
- Distributed-friendly: many LBs each doing P2C don't pile onto the same server, because each one compares a different random pair.
- It never picks the worst server (the worst one always loses its comparison).

**Honest caveat (HAProxy benchmark, 2019):**
- P2C peak connection counts ~**30% lower than round robin**.
- True least-conn was still ~**4% better than P2C** when a single LB has exact counts.
- HAProxy's conclusion: *"Power of Two was designed as a poor man's Least Connections"* — use it when you have **many LBs / sidecars / stale data**; with one central LB and exact counts, least-conn is still fine.

**Who uses it:**
| System | Config |
|---|---|
| Envoy / Istio | `LEAST_REQUEST` — P2C by default (`choice_count: 2`) |
| NGINX | `random two least_conn;` (since 1.15.1) |
| HAProxy | `balance random` defaults to `random(2)` |
| Netflix Zuul | choice-of-2 using a score from **server-reported utilization** + probation for erroring hosts |
| Linkerd, Finagle | P2C over EWMA latency ("peak EWMA") |

**Weighted variant (Envoy):** when weights differ, Envoy uses `weight = lb_weight / (active_requests + 1)^active_request_bias` (bias default 1.0; 0.0 = plain WRR).

## 6. Session stickiness (affinity)

**What:** the same client keeps going to the same backend.

**How it's implemented:**
| Method | Example | Gotcha |
|---|---|---|
| LB-generated cookie | ALB `AWSALB` (duration 1 s – 7 days, default 1 day); HAProxy `cookie SRV insert`; NGINX `sticky cookie` | Needs cookies; client must send them back |
| App cookie | ALB `AWSALBAPP` keyed on your app's session cookie | App controls lifetime |
| Source IP hash | NGINX `ip_hash` (first 3 octets of IPv4), HAProxy `balance source` | Everyone behind one corporate NAT / CDN / mobile carrier looks like one client → hotspot; mobile users change IP → lose affinity |
| Hash on key | NGINX `hash $cookie_user consistent`, Envoy `RING_HASH`/`MAGLEV` | Good for caches/shards, see consistent hashing |

**Why it's needed:**
- Legacy apps with **session in RAM** (login, shopping cart, multi-step wizard).
- **Local cache warmth** — the backend already has this user's data.
- Protocols with server-side state: WebSocket rooms, multi-part uploads, SignalR/Socket.IO long-polling fallback.

**Why it's dangerous:**
1. **Uneven load** — a few heavy users / one big NAT'd office pin one server at 100% while others idle. The algorithm can no longer route around a hot server.
2. **Scale-out doesn't help** — new servers from autoscaling get only *new* sessions; existing hot sessions stay put (1-day cookie = up to a day to rebalance).
3. **Server dies → sessions die** — everything stored on it is gone; users are logged out / lose their cart.
4. **Deploys get slow and painful** — you must drain until sticky sessions expire, or cut users off.
5. **Hides a stateful design** — it's a crutch that makes the app look stateless when it isn't.

**What to do instead / how to use it safely:**
- Move session state out: Redis / DB session store, or stateless tokens (JWT).
- Treat stickiness as a **performance hint, not a correctness requirement** — the app must still work if the user lands on another server.
- **Consistent hashing with bounded loads** (Google Research 2016): keep affinity, but if the preferred server is more than *c×* average load, spill to the next one. HAProxy `hash-balance-factor` (contributed by Vimeo, 1.7+) — Vimeo cut cache bandwidth by almost **8×**.
- Keep cookie durations short.

## 7. Comparison table (candidate summary slide)

| Algorithm | State | Handles slow backend? | Affinity? | Cost / pick | Use when |
|---|---|---|---|---|---|
| Random | none | no | no | O(1) | Stateless, many LBs, quick & simple |
| Round robin | 1 counter | no | no | O(1) | Identical servers, uniform requests |
| Weighted RR (smooth) | counter + weights | no | no | O(n) | Mixed instance sizes, canary % |
| Least conn | in-flight per server | yes | no | O(n) | One LB, variable request cost |
| **P2C** | in-flight per server | yes | no | O(1) | **Default for L7 / many LBs / sidecars** |
| Sticky / hash | cookie or ring | no | yes | O(1)–O(log n) | Caches, shards, legacy session-in-RAM |

## 8. Hook into the demo ("The Crashed Server")

- NGINX default = round robin → requests cycle 8001 → 8002 → 8003 (the goal of the exercise).
- Extra beats you can show live by changing one line in `upstream`:
  - `weight=3` on 8001 → see `1 1 2 1 3 1 …` (smooth WRR interleaving, not `1 1 1 2 3`).
  - `random two least_conn;` → P2C.
  - `ip_hash;` or `hash $remote_addr consistent;` → all your curls stick to one server (all from 127.0.0.1 → shows the NAT hotspot problem!).
  - `sticky cookie srv_id;` — now available in open-source NGINX (was NGINX Plus-only before 1.29.6).
- **Crash** one server (kill 8002): passive failure detection via `max_fails=1 fail_timeout=10s` (defaults) — NGINX retries the next upstream and marks 8002 down for 10 s. With `ip_hash`, users pinned to 8002 get re-hashed; with in-memory sessions they'd lose them → ties stickiness danger to the demo.
