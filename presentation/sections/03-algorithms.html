3.1 · What is a load balancing algorithm?

Health checks decide which servers are allowed. The algorithm picks one of them for this request, using whatever information it has.

The balancer looks at…AlgorithmType
the order requests arrive inRound robinstatic
the capacity you configuredWeighted round robinstatic
live connection countsLeast connectionsdynamic
who the client is (IP)IP hashstatic
  • Static: fixed rules, blind to what servers are doing right now. Dynamic: reads live server state.
  • For each one, ask two things: what does it know, and what does it ignore? The ignored part is where it breaks.

3.2 · Round robin

Next server in the list, then wrap around. Every server gets the same number of requests.

  • knows One counter: servers[i++ % N].
  • good Simplest possible, almost no state. The default in NGINX, HAProxy and AWS ALB.
  • ignores How long each request takes. A 3 s export and a 5 ms health check are both "one turn".
  • use when Servers are the same size, requests cost about the same, and the app is stateless.

3.3 · Weighted round robin

Server A is 3× bigger, so it gets 3 turns for every 1 turn of B and C.

  • knows A weight per server, set by you: server a weight=3;
  • use when Mixed instance sizes during a migration, or a canary split (90% v1, 10% v2).
  • smooth NGINX interleaves the turns (A B A C A) so A never gets a burst.
  • ignores Live load. A weight is what you believe a server can handle, not a measurement. Set it wrong and that server overloads.

3.4 · Least connections

Send to the server with the fewest active connections right now. A slow server finishes fewer, so it gets fewer.

  • Server B is in a GC pause: each request takes 5 s instead of 1 s.
  • round robin Still sends B every third request. They pile up.
  • least conn Sees B is busy and goes elsewhere. No config change needed.
  • cost The balancer must track live counts per server. A brand-new server has 0 connections and gets flooded (use slow start).
  • use when Request times vary a lot or connections are long-lived: WebSockets, uploads, DB proxies.

3.5 · IP hash

Hash the client's IP to pick the server. The same user always lands on the same server, with no table to store.

  • knows The client: server = hash(ip) % N.
  • gives Session affinity: round 2 finds each user's session on the same server.
  • NAT An office of 50 people behind one IP is "one client". They all hit server A.
  • NGINX ip_hash uses only the first 3 octets of an IPv4 address, so a whole /24 shares one server. Mobile users change IP and lose affinity.

3.6 · IP hash when servers change

Add one server and % N sends most users somewhere new. Lose one server and its users lose their sessions.

  • 3 servers, each user's session on one of them.
  • add D % 3 becomes % 4. About 75% of users move to a new server that has no session for them. Alex Xu calls this the rehashing problem (ch. 5).
  • B dies B's users go to another server, which doesn't have their sessions either.
  • less bad Consistent hashing moves only ~1/N of users (ch. 5; see appendix). NGINX hash $remote_addr consistent;

3.7 · Sticky sessions: stateful vs stateless

IP hash only matters because the server holds the session. Move the session out and any server can take any request.

  • Alex Xu, ch. 1: with stateful servers, every request from a client must go to the same server. Sticky sessions do that, but adding or removing servers gets harder and server failures are hard to handle.
  • Most balancers pin with a cookie instead of the IP (ALB AWSALB, HAProxy cookie SRV insert, NGINX sticky cookie). It survives IP changes, but has the same problems.
  • fix · ch. 1 Keep session data in shared storage (Redis, NoSQL, a DB). The web tier becomes stateless and easy to scale.
  • Still want affinity? Use it only as a cache hint: losing it should cost a cache miss, not a logout.

3.9 · How to choose

Pick the algorithm by the information that matters for your traffic.

round robin
Order

"Whose turn is it?"

Same-size servers, similar requests.

weighted round robin
Capacity

"Who is bigger?"

Mixed server sizes, canary splits.

least connections
Load

"Who is least busy now?"

Request times vary, long connections.

ip hash
Identity

"Who is this client?"

Must keep a user on one server.

Reaching for sticky sessions? First ask whether you can make the app stateless instead.

Appendix · Power of two choices

Pick two backends at random, send to the less busy one

// Envoy LEAST_REQUEST does this by default (choice_count = 2)
fun pick(pods: List<Pod>): Pod {
  val a = pods.random()
  var b = pods.random()
  while (b == a) b = pods.random()
  return if (a.inFlight <= b.inFlight) a else b
}
  • Scanning all 200 pods for the minimum costs O(n) per request. Two random picks cost O(1).
  • It still avoids the worst pod: a stuck pod only wins when it is compared with a pod that is even worse.
  • It also fixes the herd: with several balancers, each only knows its own in-flight counts. Random pairs keep them from all choosing the same "idle" pod at once.
  • Result: close to least-connections quality, at round-robin cost. A good default for L7.

Appendix · Consistent hashing

Put nodes and keys on one ring. A key belongs to the next node clockwise.

  • Hash each node's name to a point on a ring of 232 positions. Hash each key the same way.
  • Walk clockwise from the key; the first node you meet owns it.
  • Add node D: only keys between C and D change owner, and they all move to D. Everything else stays put — about 1/N of the keys move.
  • With 3 points the arcs are uneven. Give each node 100–200 virtual nodes (A#0 … A#149) so every node owns about the same share.
