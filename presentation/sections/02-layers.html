Layers

A request is balanced several times before it reaches your code. Each hop sees different information and can make a different decision.

2.1 · DNS

Return several IPs and let the client pick. Cheap, but clients keep a dead IP until the TTL runs out.

$ dig +short api.shop.vn
10.0.1.11
10.0.1.12
10.0.1.13
# resolver rotates the order on each lookup

$ dig api.shop.vn | grep TTL
api.shop.vn.  300  IN  A  10.0.1.11

# 12:00:00  10.0.1.12 dies
# 12:00:00  record removed from the zone
12:04:59  clients still send to 10.0.1.12  5 min of errors
  • good at Sending users to the nearest region: Route 53 latency or geo routing.
  • bad at Reacting fast. Resolvers, OS caches and JVMs cache the answer for the TTL, some for longer.
  • No health, no load info: the client can't tell a busy IP from an idle one.
  • Use DNS to pick a region, then a real balancer inside it to pick a server.

2.2 · L4 vs. L7

An L4 balancer sees IPs and ports. An L7 balancer reads the HTTP request.

L4 · transportL7 · application
BalancesConnectionsRequests, even many on one connection
Can route byIP, portPath, host, header, cookie, method
TLSPasses it throughTerminates it; can re-encrypt to the pod
CostVery low, millions of connectionsParses every request; more CPU per request
ExamplesAWS NLB, HAProxy mode tcp, kube-proxyAWS ALB, Envoy, NGINX, HAProxy mode http

2.3 · What L7 buys you

One address, many pools. Route by path, header, or weight.

# NGINX-style, one listener on :443
location /api/          { proxy_pass http://api_pool; }
location /ws/           { proxy_pass http://socket_pool; }
location /static/       { proxy_pass http://cdn_origin; }

# canary: 5% of /api/ goes to v2
split_clients $request_id $api_version {
  5%   api_v2;
  *    api_v1;
}

# internal testers always get v2
if ($http_x_canary = "true") { set $api_version api_v2; }
  • path /api and /ws scale separately, on different pod types.
  • weight Ship v2 to 5% of requests, watch the error rate, then 25%, 100%.
  • header QA sends X-Canary: true to test v2 in production.
  • An L4 balancer can do none of this: it never sees the path. It can only pick a server for the whole connection.

2.4 · The path on AWS EKS

Four hops pick a destination before a request reaches a pod

LayerDefault algorithmHealth signal
① Route 53DNSLatency, geo, or weighted recordsRoute 53 health checks
② ALBL7Round robin; can switch to least outstanding requestsTarget group health check
③ IngressL7Round robin (NGINX); Envoy also offers least request, ring hashPod readiness via Endpoints
④ ServiceL4iptables: random pick per connection · IPVS: round robinPod readiness only
  • External traffic can skip hop ④. With the ingress sending straight to pod IPs, the Service is only used for internal pod-to-pod calls — and there it balances connections, not requests (section 5).

2.5 · Client-side balancing

For service-to-service calls, the caller can pick the backend itself and skip a hop

  • A gRPC client with round_robin and a headless Service opens one connection per pod and spreads calls itself.
  • A service mesh (Istio, Linkerd) puts an Envoy-like proxy next to every pod. Your code calls localhost; the sidecar balances.
  • The cost: every client needs the pod list, and must refresh it when pods come and go. Stale lists send calls to pods that no longer exist.
