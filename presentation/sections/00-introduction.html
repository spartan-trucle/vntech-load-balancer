The pain

One server fails on three separate axes, not one

① Capacity
You run out of machine

CPU, RAM, file descriptors, concurrent connections. A 64 vCPU box still has one NIC, and the next size up costs more per core.

queue builds → timeouts cascade
② Availability
Change you did not ask for

One crash, one kernel panic, one AZ losing power = 100% down. Running 3 instances fixes nothing until something notices the dead one.

3 instances = 3 ways to fail
③ Operability
Change you did ask for

Deploys, patches, config rollouts, rollbacks. With one server each one is an outage, and you do this every week — not once a year.

no canary, no rollback path

Capacity is how much you can serve. Availability is surviving change you did not ask for. Operability is making change you did ask for, safely. Most of your changes are planned — that is why operability bites even a service that fits on one box.

What a load balancer is

For each request, pick one healthy backend from a pool. Skip the ones that are down.

# pool: api · algorithm: round robin
12:00:01.010  GET /orders/81  → pod-a  200  42 ms
12:00:01.013  GET /orders/82  → pod-b  200  39 ms
12:00:01.500  health  pod-b   → timeout ×3 → DOWN
12:00:01.502  GET /orders/84  → pod-c  200  # pod-b skipped
12:00:01.509  GET /orders/85  → pod-a  200
  • Health checks decide who is allowed; the algorithm picks which one of those.
  • Clients never learn the backend IPs, so you can add, remove or restart pods without anyone changing config.

Vocabulary that gets confused

Forward proxy, reverse proxy, load balancer: same machinery, different direction

Every load balancer is a reverse proxy; a reverse proxy with one upstream is not. NGINX, HAProxy and Envoy are all three, by config.

  • To the client the LB is the server; to the backend it is the client — the backend sees the LB's IP, not the user's. Pass the real one in X-Forwarded-For (L7) or PROXY protocol (L4).

What you actually get

Three jobs: spread the load, route around failure, hide deploys

Spread
No backend gets more than its share

600 req/s across 3 pods is ~200 each, not 600 on one and 0 on two.

Route around failure
A dead pod stops getting traffic

Health checks and error counts take a failing backend out of the pool in seconds, and put it back when it recovers.

Hide change
Deploy without users noticing

Drain one pod, replace it, add it back. Canary 5% of traffic to v2. Clients see one stable address.

It usually does more: TLS termination, HTTP/2 to clients, compression, WAF rules. Those are features of the box, not of load balancing.

Types of load balancer

Six names you will meet, sorted by three questions: what runs it, what it reads, how far it reaches

By what runs it
Appliance, program, or managed service

Hardware · F5 BIG-IP, Citrix ADC
A physical box in the rack with custom chips. Fast, expensive, sized once.

Software · NGINX, HAProxy, Envoy
A program on any VM or pod. Scale it by running more copies.

Cloud · AWS ALB/NLB, Google Cloud Load Balancing, Azure Load Balancer
The provider runs it. You get an endpoint and a bill per hour and per GB.

By what it reads
A port, or the HTTP request inside

Layer 4 · transport
Reads the IP address and TCP/UDP port. Picks a backend once per connection. AWS NLB.

Layer 7 · application
Reads the method, path, headers and cookies. Picks a backend per request. AWS ALB.

part 1 how each one works

By how far it reaches
One data center, or the whole planet

Local · one cluster or region
Backends are milliseconds apart and one balancer sees all of them.

Global (GSLB) · across regions
Picks a region for the user, usually through DNS or anycast, before any local balancer is reached.

part 2 DNS, anycast, edge proxies

One box is usually several of these at once: an AWS ALB is cloud, software underneath, and layer 7. The questions are independent.

Scale up vs. scale out

A bigger box has a ceiling and one power cord. More boxes need a balancer.

Scale up · vertical
Move from 4 vCPU to 64 vCPU

No code change. Stops at the biggest instance type, costs more per core near the top, and one host failure is a full outage.

simplesingle point of failure
Scale out · horizontal
Run 16 pods of 4 vCPU each

Add pods as traffic grows, lose one without an outage. Needs a balancer in front and an app that keeps no user state in memory.
