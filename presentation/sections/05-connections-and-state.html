Connections & state

The algorithm assumes every request is free to go anywhere. Sessions, long-lived connections and keep-alive break that assumption.

5.1 · Sticky sessions

A cookie pins each user to one pod. It fixes in-memory sessions and breaks everything else.

# first response from the ALB
HTTP/1.1 200 OK
Set-Cookie: AWSALB=pod-b…; Expires=+7d

# every later request from this browser
Cookie: AWSALB=pod-b…   → pod-b, always

# 14:00  pod-b is replaced by a deploy
Cookie: AWSALB=pod-b…   → pod-a
GET /cart → { items: [] }  cart lost
  • uneven A few heavy users stuck on one pod keep it hot while the others idle. The algorithm can't move them.
  • fragile Every deploy, scale-in or crash logs users out or empties carts.
  • fix Keep sessions in Redis or a signed JWT. Any pod can serve any request, and stickiness becomes unnecessary.
  • Stickiness is still fine as a cache hint (a warm per-user cache), as long as losing it only costs a cache miss.

5.2 · Long-lived connections

An L4 balancer picks a pod per connection. gRPC sends every call over one connection.

  • HTTP/2 multiplexes thousands of calls on one TCP connection. The Service balanced the connection once, at startup.
  • Scaling out doesn't help: new pods get no traffic until some client reconnects.
  • fix Balance per call: a mesh sidecar, an L7 proxy, or gRPC round_robin with a headless Service.
  • and Set a max connection age on the server (gRPC MAX_CONNECTION_AGE, e.g. 5 min) so clients reconnect and pick up new pods. WebSockets need the same: close with jitter and let clients reconnect.

5.3 · Keep-alive timeouts

If the pod closes an idle connection before the balancer does, some requests get a random 502

# ALB idle timeout: 60 s   ·   Node.js keepAliveTimeout: 5 s

12:00:00.000  ALB → pod  conn #7  GET /orders  → 200
              # conn #7 idle, ALB keeps it for reuse
12:00:05.000  pod closes conn #7 (idle 5 s)
12:00:05.001  ALB → pod  conn #7  GET /cart   → 502
              # request was in flight when the FIN arrived

# fix: backend timeout > balancer timeout
server.keepAliveTimeout = 65_000   // > ALB 60 s
server.headersTimeout   = 66_000
  • Low rate, random, and never reproducible locally: a handful of 502s a day, with no error in the app logs.
  • The rule: whoever opens the connection must close it first. The balancer opens it, so the backend's idle timeout must be longer.
  • Check the default of whatever you run behind the balancer (Node.js, Gunicorn, Netty, Tomcat). Several are shorter than 60 s.
