6.4 · Losing a region

DNS failover is bounded by the TTL. Anycast is bounded by BGP.

# Singapore goes dark at 10:00:00

10:00:30  Route 53 health check: 3 fails → SIN removed
10:00:30  new lookups get Tokyo only
10:01:30  TTL 60 s expired for most resolvers
10:05:00  a few clients still on SIN  # ignore TTL

# Tokyo now receives 2× traffic
10:00:40  Tokyo Envoy p99  90 ms → 310 ms
10:01:10  HPA adds pods (takes ~60–90 s)
10:02:30  Tokyo p99 back to 110 ms
  • DNS Simple, works with any backend. Failover ≈ detection (~30 s) + TTL (60 s) + stragglers.
  • anycast One IP announced from every region (AWS Global Accelerator, Cloudflare). Routers pick the nearest; failover in seconds.
  • the real trap Failover moves the traffic, not the capacity. If Tokyo can't take 100% right now, you've turned one region outage into two.

6.5 · Capacity

Size each region for the whole world, then add room to lose a node

peak 200,000 req/s global
one region down → survivor takes 200,000
Envoy node: 25,000 req/s at 60% CPU (measure yours)
200,000 ÷ 25,000 = 8 nodes
+ lose 1 AZ of 3 → × 1.5 = 12
per region: 12 nodes, normally at ~33% of rated load
  • Run the balancer tier at 30–40% in normal times. That idle headroom is what makes failover a non-event.
  • Count connections too, not only requests: 400,000 open WebSockets × ~50 KB is 20 GB of memory across the fleet.
  • Then prove it: game-day drill, drain one region on purpose in business hours, watch p99 and 5xx.
