Local load balancing

Inside one data center: what an L4 balancer and an L7 balancer actually do to your traffic, how they check that a backend is alive, and how to choose.

10 / 54section 1 · local load balancing
1.1 · Back to the OSI model

Seven layers, two seats for a balancer: layer 4 is an NLB, layer 7 is an ALB

  • L4 The balancer reads the TCP header only: source IP, destination port. It picks one backend when the connection opens, then copies bytes. On AWS that is the NLB.
  • L7 The balancer terminates TLS and parses every HTTP request: method, path, Host, cookies. It can pick a different backend per request. On AWS that is the ALB.
  • Same idea outside AWS: HAProxy mode tcp and kube-proxy sit at L4; NGINX, Envoy and HAProxy mode http sit at L7.
  • Layers 5 and 6 barely exist in practice — TCP/IP folds them into TLS. Every choice in this section is really "L4 or L7?".

1.2 · What is actually on the wire

A packet is not a request. Turning one into the other is the whole L4 / L7 difference.

  • Think of the post. L3 is the street address on the envelope: which machine.
  • L4 is the apartment number, plus "this is envelope 3 of 7, open them in order".
  • L7 is the letter inside. The postal service never reads it — and reading it is real work somebody has to do.
  • One request can span many packets; one packet can hold the tail of one request and the head of the next. Nothing on the wire marks where a request begins.

1.3 · How an L4 balancer works

It chooses once, at the SYN, writes the choice in a table, then just shovels packets

  • state One row per flow: (src ip, src port, dst ip, dst port) → pod. Packets 2..N carry no routing hint, so the table is the only memory of the choice.
  • tls Encrypted bytes forward exactly like plain ones — it was never going to read them. The one L7-ish signal it gets is SNI, sent in the clear during the handshake, which is how L4 does per-domain routing while holding no keys.
  • cost Restart the balancer and the table is gone: every live connection resets. And it kept no copy of the bytes, so it can never retry.

1.4 · How an L7 balancer works

It is two TCP connections glued together by a program that read your request

  • per request Two requests on the same client connection can land on two different pods. An L4 balancer cannot do that — it already committed the whole pipe.
  • tls It must decrypt: no plaintext, no HTTP to parse. So the private key and cert rotation move to the balancer, and the hop to the pod is plaintext unless you re-encrypt.
  • retry It still holds the request in memory, so when a pod dies it writes the same bytes to another one. The client never learns anything went wrong.

1.5 · Where your request waits

An L7 balancer keeps a copy of your request in memory — and memory runs out

  • The balancer is an ordinary program, like the ones you write. It reads the request in, decides where it goes, writes it out. While it decides, the request sits in its memory.
  • the limit 10,000 requests at once × 64 KB is 640 MB. At 10 MB each it would be 100 GB — so every balancer caps how much of a request it will keep.
  • gotcha Over the cap it stops keeping a copy and just passes the bytes along. Now there is nothing to re-send, so retries quietly stop working — and a big upload to a pod that dies fails.
  • An L4 balancer never keeps anything: it forwards each packet and forgets it. That is why it costs so much less, and why it could never retry.

1.6 · Health checks

The balancer has to keep asking "are you alive?" — and the answer is never instant

  • active Probe on a timer. interval 5s × 3 failures = ~15 s of errors before ejection — plus the request already in flight. Sane default: 5 s, 3 out, 2 back in.
  • passive Watch real traffic and eject on errors. Free, and it catches the case active misses: /healthz returns 200 while every real request 500s. Run both.
  • gotcha Never check the database inside /healthz. A 2 s DB blip fails every pod at once and turns "degraded" into "100% down". Keep the check shallow.

1.8 · So which one do you pick?

Pick by what the balancer needs to know — then fix the defaults that bite

pick L4 · NLB

It isn't HTTP: Postgres, Redis, Kafka, MQTT, game UDP.

You need a static IP, millions of idle connections, or TLS that reaches the backend untouched.

flow hash, not tunable
client IP preserved
idle 350 s · adds ~100 µs
absorbs a 10× spike
pick L7 · ALB

You route by path, host, header or cookie.

You want retries, canary weights, or p99 per route. Most web and API traffic starts here.

round robin by default
client IP in X-Forwarded-For
idle 60 s · adds ~1–4 ms
needs warm-up for a spike
use both

A cheap L4 layer at the edge absorbs the connections; a fleet of L7 proxies behind it does the routing.

1.9 · What L7 buys you

One hostname on the outside. Inside, you can send any request anywhere you like.

  • scale them apart /api is CPU-bound and /ws holds connections for hours. Same hostname, different pod types, different autoscaling rules — and no client ever knows.
  • ship safely Send 5% to v2, watch the error rate, go to 25%, then 100%. Rollback stops being a redeploy and becomes one number back to zero.
  • test in production QA sends a header and lands on v2 every time, against real data, while everyone else stays on v1.

1.11 · Client-side balancing

For service-to-service calls, the caller can pick the backend itself and skip a hop

  • A gRPC client with round_robin and a headless Service opens one connection per pod and spreads calls itself.
  • A service mesh (Istio, Linkerd) puts an Envoy-like proxy next to every pod. Your code calls localhost; the sidecar balances.
  • The cost: every client needs the pod list, and must refresh it when pods come and go. Stale lists send calls to pods that no longer exist.
