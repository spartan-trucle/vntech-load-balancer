1.1 · Back to the OSI model

Seven layers, two seats for a balancer: layer 4 is an NLB, layer 7 is an ALB

  • L4 The balancer reads the TCP header only: source IP, destination port. It picks one backend when the connection opens, then copies bytes. On AWS that is the NLB.
  • L7 The balancer terminates TLS and parses every HTTP request: method, path, Host, cookies. It can pick a different backend per request. On AWS that is the ALB.
  • Same idea outside AWS: HAProxy mode tcp and kube-proxy sit at L4; NGINX, Envoy and HAProxy mode http sit at L7.
  • Layers 5 and 6 barely exist in practice — TCP/IP folds them into TLS. Every choice in this section is really "L4 or L7?".

1.3 · What L7 buys you

One address, many pools. Route by path, header, or weight.

# NGINX-style, one listener on :443
location /api/          { proxy_pass http://api_pool; }
location /ws/           { proxy_pass http://socket_pool; }
location /static/       { proxy_pass http://cdn_origin; }

# canary: 5% of /api/ goes to v2
split_clients $request_id $api_version {
  5%   api_v2;
  *    api_v1;
}

# internal testers always get v2
if ($http_x_canary = "true") { set $api_version api_v2; }
  • path /api and /ws scale separately, on different pod types.
  • weight Ship v2 to 5% of requests, watch the error rate, then 25%, 100%.
  • header QA sends X-Canary: true to test v2 in production.
  • An L4 balancer can do none of this: it never sees the path. It can only pick a server for the whole connection.

1.5 · Client-side balancing

For service-to-service calls, the caller can pick the backend itself and skip a hop

  • A gRPC client with round_robin and a headless Service opens one connection per pod and spreads calls itself.
  • A service mesh (Istio, Linkerd) puts an Envoy-like proxy next to every pod. Your code calls localhost; the sidecar balances.
  • The cost: every client needs the pod list, and must refresh it when pods come and go. Stale lists send calls to pods that no longer exist.
