4.2 · NGINX as the balancer

One upstream block with three servers. No algorithm line means round robin.

demo/nginx/nginx.conf · simplified
events {}
http {
  upstream backend {
    # no directive here = round robin
    server 127.0.0.1:8001;
    server 127.0.0.1:8002;
    server 127.0.0.1:8003;
  }
  server {
    listen 8000;
    location / { proxy_pass http://backend; }
  }
}
send 6 requests

4.5 · Why nobody saw the crash

Kill 8002. The client sees no error: NGINX retries the next server and stops sending to 8002 for 10 s.

npm run crash -- 8002   # SIGKILL the 8002 backend

for i in $(seq 6); do curl -s localhost:8000; done
Server 8001
Server 8003      # 8002 refused → retried on 8003
Server 8001
Server 8003
Server 8001
Server 8003
  • Connection refused counts as a failure. NGINX passes the request to the next server (proxy_next_upstream error timeout, the default).
  • Defaults: max_fails=1, fail_timeout=10s. One failure takes 8002 out for 10 s, then NGINX tries it again.
  • npm run revive -- 8002 and it's back in rotation after the next try. This is passive checking: NGINX only notices when real traffic fails.
  • Try it with ip_hash;: users who were on 8002 move to another server. With sessions in memory, they'd be logged out.
