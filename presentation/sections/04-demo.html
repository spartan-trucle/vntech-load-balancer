4.1 · Setup

Three Node servers behind NGINX, running on this laptop. The live slide sends them real requests; nothing is simulated.

  • cd demo && pnpm start starts the three servers and NGINX. The deck calls NGINX with fetch(); NGINX picks a server with whichever algorithm is live.
  • NGINX adds two headers: X-Upstream (every server it tried, in order) and X-LB (the algorithm). The coins on the live slide are drawn from them.
  • The deck also asks each server /__health directly, so a server you crash turns red within a second.

4.2 · What's actually running

One NGINX config and a 30-line Node server. Everything the live slide shows comes from these two files.

demo/nginx/nginx.conf · trimmed
upstream backend {
  include generated/upstream.conf;
  # pnpm algo least writes: least_conn;
  # server 127.0.0.1:8001; … 8002; … 8003;
}
server {
  listen 8000;
  location / {
    proxy_pass http://backend;
    proxy_buffering off;   # headers pass through at once
    proxy_next_upstream error timeout;
    # every server tried: "…:8002, …:8003"
    add_header X-Upstream $upstream_addr always;
    add_header X-LB $lb_algorithm always;
    add_header Access-Control-Allow-Origin * always;
  }
}
demo/src/server.ts · trimmed
createServer((req, res) => {
  if (url.pathname === '/__health')
    return res.writeHead(204).end();

  if (url.pathname === '/__control')  // pnpm slow 8002 3000
    delayMs = Number(url.searchParams.get('ms'));

  res.writeHead(200, { 'X-Server': String(port) });
  res.flushHeaders();  // NGINX knows who took it now
  setTimeout(() =>
    res.end(`Server ${port}\n`), delayMs);
}).listen(port, '127.0.0.1');
  • pnpm crash 8002 is a real kill -9 of that Node process. NGINX finds out the same way it would in production: a refused connection.

4.5 · Why nobody saw the crash

Kill 8002. The client sees no error: NGINX retries the next server and stops sending to 8002 for 10 s.

npm run crash -- 8002   # SIGKILL the 8002 backend

for i in $(seq 6); do curl -s localhost:8000; done

  • Connection refused counts as a failure. NGINX passes the request to the next server (proxy_next_upstream error timeout, the default): the L7 retry from slide 15.
  • Defaults: max_fails=1, fail_timeout=10s. One failure takes 8002 out for 10 s, then NGINX tries it again.
  • npm run revive -- 8002 and it's back in rotation after the next try. This is passive checking (slide 17): NGINX only notices when real traffic fails.
  • Try it with ip_hash;: users who were on 8002 move to another server. With sessions in memory, they'd be logged out.
